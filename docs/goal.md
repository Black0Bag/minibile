# 项目总目标（Goal）

> 状态：目标澄清完成，等待 L3 总计划确认后进入业务代码实施。
> 基线：`Black0Bag/minibile` 的 `main` 分支，起始提交 `f323d6c5`。

## 项目背景

当前代码是一个面向通用场景的 Android Agent 平台，包含手机控制、语音、视觉、虚拟形象、日常生活工具、工作流、市场、开发环境和多种外部集成。功能覆盖很广，但产品重心不集中，界面、工具、模型配置和运行时都承担了大量与编码无关的职责。

本项目将以当前尚未定制的源码和正在运行的原始应用为一次性行为基线，进行完全独立的产品重构：

- 不再同步上游代码
- 与其他项目完全独立，不建立业务、架构、命名或记忆关联
- 不要求兼容现有聊天、配置、记忆、工作区或数据库数据
- 代码开始定制后，原始应用行为不再作为新系统的事实源；新的文档、GitHub Actions 测试、签名构建、Release 产物和验收记录成为唯一事实源

目标用户只有仓库所有者本人。产品不追求通用助手能力，只追求 VibeCoding 场景下的深度、可靠性、可观察性和操作效率。

## 总目标

将当前通用 Agent 平台彻底重构为一个简体中文优先、覆盖各种软件项目类型、专门服务 VibeCoding 的 Android 编码 Agent。

目标工作流如下：

```text
绑定或创建项目
	→ 用户手动选择 Plan 模式
	→ Agent 只读分析代码、运行只读终端命令、联网研究并委派只读 Subagent
	→ Agent 创建会话级结构化 TODO，UI 实时显示计划和进度
	→ 用户审核计划并手动切换到 Build 模式
	→ Agent 编辑代码、调用编码工具、委派执行型 Subagent
	→ 在 PRoot 中安装项目依赖、编译和测试
	→ Agent 按 TODO 逐项更新状态并展示中文工具动作
	→ 网络卡顿或用户暂停时保存可恢复执行状态
	→ 恢复后继续未完成步骤
	→ 验证结果并交付变更、证据、风险和文档
```

围绕这条工作流建立一个统一的“编码任务执行内核”，而不是把模式、TODO、Subagent 和恢复机制做成互不关联的功能补丁。

核心目标包括：

1. 建立用户独占控制的 Plan / Build 双模式
2. 建立会话级、结构化、实时可见的 TODO 运行时
3. 建立可并行、可恢复、受父会话硬权限约束的 Subagent 系统
4. 建立贯穿主代理、子代理、ToolPkg、MCP、Skill 和直接工具调用的统一权限门禁
5. 建立模型能力自动发现与可信来源标记
6. 建立简体中文工具显示和任务可观察性
7. 建立暂停、卡顿检测、检查点和继续执行机制
8. 保留所有可能服务 VibeCoding 的开发能力
9. 从代码、资源、依赖、权限和界面中彻底删除与 VibeCoding 无关的通用 Agent 能力

## 成功标准

### 功能成功标准

1. 支持 Android、Web、Python、Go、Node.js、Java、Flutter、TypeScript 及其他可通过工作区和 PRoot 开发的项目，不设置人为语言边界
2. Plan / Build 只能由用户在 UI 中手动切换；Agent、Subagent、ToolPkg、MCP、Skill、Prompt 和工具调用均不能切换模式
3. Plan 模式可读取项目、搜索代码、运行受约束的只读终端操作、访问互联网、调用只读 Subagent，并更新会话级 TODO；不能修改项目、环境、Git 状态或外部系统
4. Build 模式具备完整编码能力，但仍受用户配置的工具审批和安全规则约束
5. 每个复杂任务都有输入框附近可展开的 TODO UI，实时显示完成数量、当前项和完整列表
6. TODO 至少支持 `待处理`、`进行中`、`已完成`、`已取消`；工作未结束时同时只能有一项处于 `进行中`
7. 主代理可创建前台或后台 Subagent 任务，查看父子关系、运行状态、结果和失败原因，并可继续既有子任务
8. Plan 会话创建的所有 Subagent 都继承 Plan 的只读硬上限，不能通过自定义 Agent、插件或嵌套任务扩大权限
9. 用户界面不直接暴露 `use_package`、`super_admin:terminal`、`read_file_part`、`package_proxy` 等协议标识，而是显示准确的简体中文名称、动作和目标；调试详情仍可查看原始 ID
10. 模型列表自动读取服务端实际返回的上下文长度、最大输出、推理强度、支持参数和模态等元数据；服务端没有提供的字段明确显示“未知”，不得猜测
11. 用户可暂停当前编码任务；网络长时间无数据时 UI 能识别卡顿；继续操作不要求用户手动再输入“继续”
12. PRoot 终端、文件工具、Git/GitHub、互联网研究、浏览器预览、记忆、MCP、Skill、ToolPkg、Logcat、APK 安装和项目测试能力可用于编码任务
13. 手机日常控制、语音交互、视觉/听说功能模型、虚拟形象等非编码产品能力从最终界面和可执行代码中移除

### 质量成功标准

1. 每个阶段都有可重复的编译、自动测试和真机验收证据
2. Plan 硬门禁有专门的绕过测试，覆盖主代理、Subagent、QuickJS、ToolPkg、MCP、工作流和直接 `AIToolHandler` 调用
3. TODO、模式、Subagent 和检查点状态按会话隔离；并行会话互不串扰
4. 关键状态使用单一事实源和事件流驱动 UI，不通过 Prompt 文本猜测
5. 删除功能后不存在不可达源码、无用资源、残留权限、废弃依赖、失效路由或错误文档
6. 最终 APK 可以安装并完成“分析项目 → 计划 → 修改 → 编译测试 → 交付”的端到端任务
7. 所有用户可见核心流程使用自然、明确的简体中文
8. 未知能力、失败状态和恢复动作对用户可见，不静默吞错或伪造成功
9. 每次可安装交付均由 GitHub Actions 在目标提交上完成测试和签名构建，并发布到 GitHub Release；Agent 持续跟踪失败日志并修复，直到对应新版本发布成功
10. 仓库唯一版本、App `versionName`、Git Tag、GitHub Release 和 APK 文件名严格一致；当前未定制基线统一重置为 `0.0.0`，任何不一致都会阻断发布

## 范围边界（做 / 不做）

### 做

- 保留并强化项目创建、导入、绑定、文件浏览、代码编辑、差异审查和工作区备份
- 保留并强化 PRoot Ubuntu、终端会话、构建工具链、包管理器和测试执行
- 保留编码所需的文件、搜索、网络、Git、GitHub、浏览器预览和 Android 调试能力
- 建立以 GitHub Actions 为唯一权威 Android 构建环境的自动测试、签名、版本校验与 Release 发布链路；本地环境只负责源码编辑、静态检查和 Git 操作
- 保留记忆库，用于项目知识、编码经验和长期约束；记忆必须按当前项目边界使用
- 保留 MCP、Skill 和 ToolPkg 作为编码能力扩展机制，并纳入模式权限
- 重建 Agent 模式、任务状态、Subagent、模型能力和中断恢复基础设施
- 对功能做“保留 / 删除 / 拆分后保留”能力矩阵；凡是同时服务通用场景和编码场景的能力必须拆分用途后判断
- 在有源码证据和验证基线后分波删除无关垂直功能

### 不做

- 不保留通用手机助手定位
- 不保留以操作其他手机 App、日常生活控制、通话、短信、蓝牙、音乐或位置为目标的能力
- 不保留语音输入输出、后台唤醒、TTS、STT、虚拟形象和 Waifu 产品能力
- 不保留图像、音频和视频识别功能模型分类
- 不为现有本地数据编写兼容迁移或旧接口兼容层
- 不同步或回合并上游后续变更
- 不按目录名或表面用途盲删可能支撑开发的底层能力
- 不把运行时 TODO 写成 Markdown 文件；仓库计划文档与会话 TODO 是两套独立系统
- 不修改工具协议 ID 来实现中文化
- 不在服务端未提供模型信息时猜测参数
- 不允许 Agent 通过任何工具、提示词、子代理或间接调用自行切换 Plan / Build

## 约束条件

### 产品约束

- 单人自用，简体中文优先
- VibeCoding 能力范围不限制编程语言、框架和项目类型
- 所有产品取舍以是否直接服务编码任务闭环为唯一判断标准
- GitHub 上的当前源码是原始基线；本地聊天、配置、记忆和数据库数据可以舍弃
- 自定义 App 的安装包 ID 固定为 `io.github.black0bag.minibile`，与当前原始 App 并行安装；源码命名空间暂不做全仓迁移
- Release 签名资产按用户指定跟随本机工作区，固定保存在 Git 仓库外的工作区根级 `.release-signing/`；该位置的数据丢失风险必须由工作区索引持续明确记录

### Plan 模式硬约束

Plan 模式允许：

- 读取、列出和搜索工作区文件
- 获取 Git 状态、差异和历史等只读信息
- 运行经过明确分类和校验的只读终端操作
- 搜索互联网、读取技术文档和依赖源码
- 调用只读 Subagent
- 创建和更新当前会话的运行时 TODO
- 向用户提问并输出计划

Plan 模式禁止：

- 创建、编辑、删除、移动或覆盖项目文件
- 使用 shell 重定向、脚本解释器或其他间接方式写文件
- 安装或卸载软件与依赖
- 改变 Git 工作树、索引、分支、远端或提交历史
- 修改 Android 系统、其他 App、网络服务或外部仓库
- 调用具有写能力的 Subagent
- 通过 ToolPkg、MCP、Skill、QuickJS、工作流或直接 Executor 绕过限制

模式状态必须按会话保存。并行会话可以处于不同模式，不能使用全局布尔开关。

### 工程约束

- 模式权限必须在真正执行工具前以 fail-closed 方式校验，仅隐藏工具或修改 Prompt 不构成安全边界
- 每个 Agent 发起的工具调用必须携带会话、模式、调用者、任务和工作区上下文；缺少上下文的自动调用默认拒绝
- 子代理只能继承或收紧父会话权限，不能扩大父会话硬上限
- 协议 ID 与显示文本分离，动态包工具也必须有可解释的中文显示策略
- 先由 GitHub Actions 建立原始构建和行为基线，再开始业务源码改造；不要求在当前本地 Ubuntu/PRoot 安装 Android 构建工具链
- 仓库根目录必须建立唯一版本源；App 版本、Tag、Release 与产物名称均由它派生或校验，不允许多处手工维护
- 每个拟发布的源码提交都必须使用从未绑定过其他提交的新 SemVer；失败构建不得发布，修复后必须再次递增版本，禁止复用或移动已声明的版本
- 每个删除波次独立提交、独立验证，可通过 Git 提交回退
- 修改前读取完整调用链；发现计划与源码不一致时先更新计划并重新确认
- 未通过 L3 计划门禁前，不修改业务源码
