# 09 暂停、卡顿检测与检查点恢复

## 旧实现情况

当前对话有取消机制和处理状态，但没有用户可控的暂停、网络无数据状态、结构化检查点或一键继续。网络连接未断但长期无 Token 时，界面可能持续等待；用户只能停止并手动输入“继续”。

## 意图修正

把主代理、TODO、Subagent、模型流和工具副作用纳入统一任务生命周期。暂停是编排状态，不是假装底层 SSE 可以永久保留并从任意字节继续。

## 预期新实现

### 状态模型

至少包含：

- `RUNNING`
- `PAUSE_REQUESTED`
- `PAUSED`
- `STALLED`
- `RESUMING`
- `COMPLETED`
- `FAILED`
- `NOT_RESUMABLE`

用户暂停与网络卡顿严格分开：前者由用户触发，后者由无数据监测触发。

### 暂停语义

- 用户点击暂停后立即禁止创建新工具和新 Subagent
- 当前原子文件操作完成后停止编排，不能写一半文件
- 可安全取消的模型请求和后台等待任务取消
- 不可立即中断的外部进程显示“正在暂停”，完成当前安全边界后进入已暂停
- Agent 没有自行解除暂停的 API
- 模式状态不因暂停改变

### 卡顿识别

- 分别记录连接建立、首 Token、最近 Token、工具进度和后台任务心跳
- Provider 使用可配置但有明确默认依据的无数据阈值
- 达到阈值后进入 `STALLED`，显示卡住位置和最后可靠进度
- 不把正常长工具执行误判为网络卡顿
- UI 提供继续、等待或停止，具体可选项按当前状态决定

### 检查点

`ExecutionCheckpoint` 至少保存：

- 会话 ID、模式快照和工作区
- 当前主 TODO 与完整 TODO 状态
- 已确认完成的步骤
- 当前模型轮次和最后可靠消息边界
- 已开始/已完成工具及其副作用摘要
- 前后台 Subagent 状态和任务 ID
- 可继续动作
- 是否需要新模型请求
- 重复执行风险与用户确认要求
- 创建时间和原因

### 继续语义

- 同一任务从结构化检查点恢复，不要求用户重新输入“继续”
- 若底层连接仍可安全继续，则恢复消费同一任务
- 若必须创建新模型请求，UI 在执行前明示会重新请求并可能产生额外 Token
- 已完成的非幂等工具不自动重做
- 无法证明重复安全时请求用户确认
- 不可恢复时给出准确原因和可人工接续的信息

## 作用域候选

- `InputProcessingState.kt` 与新的统一任务状态
- `EnhancedAIService.kt` 取消和流式收集逻辑
- 各 Provider 的超时与流事件
- ToolExecutionManager 与工具生命周期事件
- TODO Repository
- Subagent TaskCoordinator
- ChatServiceCore 与前台 Service
- ChatViewModel 和输入区控制
- 检查点数据表/Repository

## 验证

- 用户在模型流、工具前、工具中、子任务中分别暂停
- 原子文件写入不会形成半文件
- 暂停后没有新副作用
- 网络无 Token 被识别，正常长工具进度不会误报
- 同一任务恢复后 TODO 和子任务关系不丢失
- 非幂等工具不会无确认重复执行
- 新模型请求前显示 Token 提示
- Build 暂停后切 Plan，恢复时必须服从新的用户模式，不得按旧 Build 权限继续未开始写操作
- 应用进程重启后可读取持久检查点

## 风险

- Provider 流式实现差异导致卡顿阈值不一致
- 原子操作边界定义不清造成数据损坏
- 恢复时重复提交 Git、上传文件或执行部署
- 后台子代理与父任务暂停状态竞态
- 检查点包含过多上下文导致数据库膨胀或敏感信息泄露

## 回滚

先实现纯状态观测和检查点记录，再启用暂停控制，最后启用恢复执行。三个阶段独立提交。任何副作用重复测试失败时禁用自动恢复，只保留明确的不可恢复提示，直到问题修复；不得伪造成功。
