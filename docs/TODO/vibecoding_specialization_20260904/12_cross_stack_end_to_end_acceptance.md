# 12 跨技术栈端到端验收

## 旧实现情况

项目宣称支持多种项目模板和编码工具，但当前没有一套覆盖 Plan/Build、TODO、Subagent、暂停恢复和模型能力的统一端到端验收。编译通过不能证明 VibeCoding 产品闭环可用。

## 意图修正

使用真实的小型项目证明不同技术栈都能完成“理解、计划、修改、测试、恢复和交付”，并量化重构前后的体积、权限和功能纯度。

## 预期新实现

### 代表项目矩阵

至少覆盖：

| 技术栈 | 代表任务 |
|---|---|
| Android/Kotlin/Compose | 修改一个可见组件，运行 JVM 测试或编译 Debug，查看 Logcat/安装结果 |
| Web/TypeScript | 修改交互组件，安装依赖，运行测试与构建，浏览器预览 |
| Python | 修复有测试的业务逻辑，创建虚拟环境并运行 pytest |
| Go | 修改 HTTP/CLI 行为并运行 `go test ./...` |
| Node.js | 修改服务或脚本并运行包管理器测试 |
| Java | 编译并运行一个带测试的项目 |
| Flutter/Dart | 静态分析、测试或目标平台构建能力验证 |

其他语言通过 PRoot 中可安装工具链与工作区文件能力覆盖，不人为限制产品支持范围。

### 每个项目的统一流程

1. 导入或创建项目
2. 用户切换 Plan
3. Agent 只读分析，调用网络和只读 Subagent
4. Agent 创建 TODO Dock 并逐项规划
5. 尝试 Plan 写入，确认底层拒绝
6. 用户手动切 Build
7. Agent 修改代码并更新 TODO
8. 视任务委派一个前台或后台 Subagent
9. 运行编译/测试并展示中文工具动作
10. 在安全阶段测试暂停和继续
11. 验证产物或运行结果
12. 完成 TODO 并输出变更、证据和风险

### 回归与指标

- GitHub Actions 签名 Release APK 构建和 JVM 单测
- 根 `VERSION`、App About 页面、APK 元数据、Tag、Release、APK 文件名与证书指纹一致
- 从上一个自定义 Release 覆盖安装到当前版本，确认数据保留与签名/`versionCode` 更新链有效
- 各代表项目自身测试
- Plan 绕过测试套件
- TODO、Subagent、恢复和模型能力专项测试
- APK 大小、冷启动时间、内存、Manifest 权限数、Gradle 模块数、路由数和工具数
- 不可达代码、未使用资源和依赖扫描
- 简体中文与无障碍检查
- 干净安装行为

## 作用域

- 独立验收样例或临时工作区
- Android 自动测试和必要的真机测试
- CI 脚本、版本/签名校验、Release 资产与验收文档
- 不在生产代码中嵌入测试密钥、Release 私钥、私有仓库或大体积样例

## 验证

最终通过条件等同于 [`../../goal.md`](../../goal.md) 的全部成功标准，且每个代表项目有：

- 输入需求
- Plan 输出与 TODO 快照
- Build 变更列表
- 编译/测试日志
- Subagent 与暂停恢复记录
- 最终产物或运行截图
- 剩余风险

失败的技术栈必须标明具体缺失能力，不能用“理论支持”代替验证。

## 风险

- PRoot 工具链下载耗时和网络波动
- 移动设备资源不足以构建大型工程
- 不同技术栈的包管理器与缓存占用较大
- 真机自动化测试易受系统版本影响
- 测试样例过于简单无法暴露实际问题

## 回滚

验收不会修改产品数据结构。失败时回到对应步骤文档修复并重跑该项目，不降低成功标准。临时样例和缓存的删除属于文件操作，需用户授权；关键日志保留在文档或 CI Artifact 中。
